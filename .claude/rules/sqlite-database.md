# SQLite のデータの持ち方

tansu のデータは SQLite 1 ファイル (既定 `$TANSU_HOME/tansu.sqlite`、`TANSU_HOME` の既定は `~/.tansu`。環境変数 `TANSU_DB` があればそのパスを優先する) にある。利用者のデータベースとプロパティの定義 (メタスキーマ) も同じファイルの中に持つ。

- **物理スキーマの定義は 1 箇所**: SQLite のテーブル定義 (CREATE TABLE) は `src/db/` のモジュールにだけ書く。コアの関数以外 (CLI・MCP・HTTP API・画面) は SQL を書かず、コアの関数を呼ぶ
- **マイグレーションは起動時に自動で当てる**: 物理スキーマの変更は、番号付きのマイグレーション (`src/db/migrations/`) として足し、`user_version` で適用済みを判定して起動時に順に当てる。利用者にスクリプトの実行を求めない。当てたマイグレーションは書き換えず、変更は新しい番号で足す
- **利用者のデータベースの定義はデータとして持つ**: 利用者が `db create` / `db schema` で作る表とプロパティは、物理テーブルを増やさず、メタスキーマのテーブル (データベース・プロパティ・行・値) のデータとして持つ。利用者の操作で DDL を実行しない
- **ファイルを開くのは tansu のプロセスだけ**: SQLite ファイルを開くのは tansu 自身の入口 (`tansu <CLI のサブコマンド>`・`tansu mcp`・`tansu serve`) で、どれも `src/db/` の同じモジュールを通して開く。Web 画面 (ブラウザ)・castle の skill・ほかのツールは CLI か HTTP API を通して読み書きし、SQLite ファイルを直接開かない (スキーマの知識の分散を防ぐ)
- **複数のプロセスが同時に開く前提で設定する**: CLI・`tansu mcp`・`tansu serve` は別プロセスとして同時に動くため、`src/db/` は開くたびに WAL モード (`PRAGMA journal_mode=WAL`) と `busy_timeout` を設定し、書き込みはトランザクションで囲む。排他が要る処理をプロセス内のメモリで管理しない
- **書き込みは冪等にする**: 同じ入力で 2 回実行しても行が増えない (取り込みの元ファイルと項目名のような自然キーで upsert する)。実行の事実を記録する `qa record` の扱いは `documents/PROJECT.md`「制約」
- **テストは一時ディレクトリを使う**: `TANSU_HOME` をテストごとの一時ディレクトリにし (DB も利用記録もその下に入る)、実際のホームディレクトリに書かない
