# 短いユーザー向け文言では句読点を原則使わない

SwiftUI・Flutter・Expo・Web などの実装で、ユーザーの目に触れる短い文言を日本語または英語で作る時は、句読点を原則使わない。ストア掲載文や広告素材にも同じ基準を適用する。

## 対象

- キャッチコピー・キャッチフレーズ
- 見出し・タイトル
- ボタンやラベルなどの短いアプリ内文言
- 箇条書きやリリースノートの短い項目

説明文や記事の段落など、複数の文からなる長文は対象外とし、通常の句読点を使う。

## ルール

- 読点やカンマで間を作らず、改行や語順で読みやすさとリズムを整える
- 句点やピリオドは、短い文言の末尾には付けない
- 句読点がないと誤読する場合、文法上必要な場合、または句読点を含む形が一般に定着している場合は使ってよい
- 英語の列挙カンマなど、意味や文法を保つために必要な記号は削らない

## 優先関係

本ルールと他の指示・既存文言が食い違う時は次のとおり扱う (起票元: https://github.com/bannzai/castle/issues/702 ):

- 新規に文言を起草する時は、既存文言のスタイルが本ルールに反していても踏襲せず、本ルールを優先する。既存文言側を直したい場合は一括修正を別タスクとして issue 化する
- issue や設計書に「確定コピー」として文言を固定する時も、書く時点で本ルールを通す (確定コピーを起草する側の義務)
- 実装時に、転記する確定コピーが本ルールに反して見える場合は、黙って転記せず一言指摘する (指示なく改変はしない)

## 適用機構

確定コピーを起草する判断点で本ルールを再提示する。オンボーディングの文言は `onboarding-design` skill、App Store スクリーンショットの文言は `appstore-screenshot-builder` skill が、文言を確定する前に本ルールを読み込んで照合する。

PostToolUse hook や commit 前チェックによる句読点密度の機械検査は採用しない。UI 文言と説明文・コードコメントを区別できず、誤読防止や文法上必要な句読点も誤検知するため。また、実装・commit 時の指摘では、issue に確定コピーとして固定された後の手戻りを防げない。

## 悪い例と良い例

### 日本語

悪い例:

```text
紙の色を、じぶんの好みに
```

良い例:

```text
紙の色を
じぶんの好みに
```

悪い例:

```text
マークダウン互換。見出しもチェックリストも
```

良い例:

```text
マークダウン互換で見出しもチェックリストも
```

### 英語

悪い例:

```text
Step away, and it locks itself
```

良い例:

```text
Step away and it locks itself
```

列挙カンマが必要な良い例:

```text
Syncs across iPhone, iPad, and Mac
```
